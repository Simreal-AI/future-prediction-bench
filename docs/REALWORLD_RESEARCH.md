# Real-world RL environments: evidence and product direction

Evidence checked on **2026-09-25**. This note examines a third product direction: agents that interact with consequential, verifiable tasks based on real software or real data. It complements the live prediction benchmark and the delayed-outcome forecasting RL environment. A real repository test or a held-out data computation can return feedback in minutes; a genuinely future event cannot be made to resolve sooner by faster computation.

The three environment-scaling routes below come from a supplied 2026 essay. They are a useful comparison, not three mutually exclusive research categories or a theorem that one route must win. In particular, the [Agentic World Modeling survey](https://arxiv.org/abs/2604.22748) calls its levels **L1 Predictor**, **L2 Simulator**, and **L3 Evolver**. L3 means revising a world model in response to evidence; it does not by itself mean generating an executable tool environment.

## Three routes and what transfers

| Route | What primary work establishes | Product use and boundary |
| --- | --- | --- |
| Learned mock of an environment | [WebWorld](https://arxiv.org/abs/2602.14721) trains a web simulator on more than one million interactions; [SWE-World](https://arxiv.org/abs/2602.03419) predicts software execution feedback; [DreamGym](https://arxiv.org/abs/2511.03773) synthesizes reasoning-based interaction experience. Their reported agent gains are on their own web or software tasks. | Candidate for curriculum or warm starts when real interaction is expensive. Generated observations and rewards need separate tests against real outcomes. A model of a future event is not the event's realized label; synthetic forecasts must not be scored as if settled. |
| Executable generated environments | [Agent World Model](https://arxiv.org/abs/2602.10090) reports 1,000 generated, database-backed environments; [ScaleEnv](https://arxiv.org/abs/2602.06820) generates interactive tasks and applies procedural checks; [Agent-World](https://arxiv.org/abs/2604.18292) combines environment discovery, task generation, and an evolving agent arena. | Good for cheap practice in tool syntax and stateful workflows. An executable generated verifier can still be wrong or reward an artifact of its synthetic distribution. Hold out genuine repositories, data, and future events to measure transfer. |
| Faster **actual** environments | [DeltaBox](https://arxiv.org/abs/2605.22781), [Crab](https://arxiv.org/abs/2604.28138), [SWE-MiniSandbox](https://arxiv.org/abs/2602.11210), and [RollArt](https://arxiv.org/abs/2512.22560) improve specific costs of real software sandboxes or large training clusters. | Most relevant to a new stateful software or data-workflow track. The current forecasting agent mainly reads web evidence and submits a probability, so it does not need per-turn filesystem/process checkpointing. These systems cannot rewind public websites or shorten the physical wait for a future outcome. |

The distinction between *real evidence*, *real execution*, and *future verification* matters. A cached search result is real evidence from its capture time. A repository test is real execution of a software task. A synthetic verifier is an executable program but remains an invented task. A prediction about next week's real world receives its ground-truth reward only after next week and authoritative resolution. We should retain these provenance classes in the data, even when they share an agent API.

### What the infrastructure papers actually measured

- [DeltaBox v2](https://arxiv.org/html/2605.22781v2), first posted 2026-05-21, reports **10.83 ms checkpoint API time** (excluding asynchronous dump completion) and **1.86 ms warm-template restore** on its event-weighted SWE-bench MCTS replays. Earlier abstract numbers of 14/5 ms use another presentation. Its in-guest process/filesystem state contract and large Linux/Firecracker host are different from our QEMU full-VM snapshot. The [official project README](https://github.com/dongyunpeng-sjtu/deltabox/blob/main/README.md) says the kernel patch, userspace controller, and benchmark artifacts are not yet public, so our cooperative guest implementation is an independent, narrower design rather than a code-level reproduction. This is a reason to benchmark checkpoint overhead if the new track branches stateful sandboxes repeatedly; it is not forecast settlement acceleration.
- [Crab](https://arxiv.org/abs/2604.28138), 2026-04-30, reports that more than 75% of turns in its studied shell/code workloads lack recovery-relevant state. Its host-side inspector cuts checkpoint traffic by up to 87%, with execution time within 1.9% of a fault-free run in those workloads. For our read-only forecasting tools, the simpler analogue is immutable evidence logging; a process snapshot is usually unnecessary. In a stateful task, a skipped checkpoint still needs a tested recovery rule.
- [SWE-MiniSandbox](https://arxiv.org/abs/2602.11210), 2026-02-11, reports around **5% of container-baseline disk use** and **25% of its environment preparation time**, with comparable task evaluation in its experiments. Its [official implementation](https://github.com/lblankl/SWE-MiniSandbox) uses Linux namespaces, `chroot`, and bind mounts. This is an option for trusted, controlled code tasks on a supported Linux host; isolation and resource limits must be validated for the actual threat model before running arbitrary generated code.
- [RollArt](https://arxiv.org/abs/2512.22560), first posted 2025-12-27, revised 2026-06-15, reports **1.31-2.05x lower training time** relative to its compared systems by mapping prefill, decoding, CPU environments, and reward work to suitable hardware and allowing bounded asynchronous operation. Its demonstration includes an Alibaba cluster above 3,000 GPUs. This motivates clean worker boundaries and stage timing here, not an immediate microservice rewrite for a small pilot.
- [Collinear's Environment-as-a-Service article](https://blog.collinear.ai/p/rl-env-as-a-service) is an architecture proposal, not a peer-reviewed checkpoint-latency or training-speed comparison. It separates the per-step data plane from scenario/version/reward governance in a control plane. Our local CI-triage simulator exercises stateful task and verifier lineage; it does not provide Collinear's remote environment fleet, dynamic users, or enterprise-tool coverage.
- [Daytona's current sandbox documentation](https://www.daytona.io/docs/sandboxes) distinguishes default Linux containers from its Linux VM class; the [persistence guide](https://www.daytona.io/docs/en/persistence/) reserves filesystem-plus-memory hot snapshots and live forks for VM sandboxes. Its advertised sub-90-ms container startup is a different class and denominator from this project's QEMU/HVF full-state restore. Our local template fan-out is an implementation of independent VM children, not a managed Daytona service or a comparison with its hosted latency.

These results concern different denominators: checkpoint latency, storage, environment preparation, training-system wall time. Multiplying their speedups would be invalid. First measure which part dominates this project's runs.

### Mechanisms implemented in this prototype

| Inspiration | Implemented mechanism | Missing mechanism |
| --- | --- | --- |

| [Crab](https://arxiv.org/html/2604.28138) | A [turn-aligned recovery journal](SEMANTIC_VM_RECOVERY.md) conservatively skips snapshots on bounded read-only turns, fsyncs an atomic host manifest, and passed a real QEMU-process-crash restore of RAM and a live process. The final selective run used 5 rather than 8 snapshots but was slower overall. A separate [completion gate](ASYNC_VM_CHECKPOINT.md) overlaps a real QEMU save with a simulated policy wait and blocks the next action until commitment. Our scheduler is independent code, not an import of the public ROLL framework or a reproduction of the RollArt deployment. |
| [SWE-MiniSandbox](https://arxiv.org/html/2602.11210) | Private Linux mount/PID namespaces and overlay repositories run **inside** one ARM64 VM. A [resident `RealWorldEnv` adapter](../examples/resident_guest_candidate/README.md) grades the pinned stateless Boltons fixture while keeping expected outputs on the host; unprivileged case processes have time, memory, process, file, and FD caps. | No general multi-repository dependency cache, container-free arbitrary-task preparation pipeline, or hostile-guest-root security proof. |
| [Daytona](https://www.daytona.io/docs/en/persistence/) | A checksum-bound reusable QEMU snapshot template spawns independent child VMs even after the parent exits. | No hosted API, warm-pool service, or native hypervisor fork. |
| [Collinear](https://docs.collinear.ai/core-concepts/sandbox) | A [local CI-triage simulator](../examples/collinear_ci_triage/README.md) copies a SQLite seed into a separate file per rollout, exposes tool calls and application-state diffs, and keeps exact reward checks on the host. | The simulator has no per-rollout Docker network/container isolation, managed Environment-as-a-Service, or networked enterprise-service suite. The separate Docker coding adapter has its own workspace boundary. |

No external sandbox provider is connected. These are local adaptations with the narrower state and trust boundaries listed above, not replications of the cited systems. The [microVM source audit](MICROVM_RESEARCH.md) and [performance comparison](PERFORMANCE_COMPARISON.md) give the actual implementation and matched local measurements.

An offline, pinned [Boltons repair fixture](../examples/realworld_boltons26/README.md) verified that sibling branches from the same checkpoint gave different correct rewards (`1` for the repair, `0` for the untouched source), kept independent workspaces, and rejected a tampered snapshot. A fixed visible check attempted to leave a background writer and `/tmp` marker; the branch began with no marker and no delayed file appeared after the original process's scheduled write. The results are integration checks, not a general isolation proof.

For the same public Boltons fixture, the [actor/verifier pipeline benchmark](../examples/realworld_boltons26/benchmark_pipeline.py) used one interaction worker, one verification worker, one hidden-case worker per episode, and a one-item verifier queue. Three scripted episodes per condition produced the expected rewards `[1, 0, 1]` in both repetitions. Alternating condition order gave serial batch times of 10.918 and 8.738 seconds, versus pipeline times of 8.640 and 7.672 seconds. The two-repetition medians are 9.828 and 8.156 seconds, a 1.205× ratio in graded environment episode throughput for this small same-host workload. Cold start and host load remain material; this is not a model-inference, optimizer, or end-to-end RL training measurement. A four-episode synthetic coding fixture repeated three times showed 2.261 versus 1.606 second medians (1.408×), but is less representative than Boltons. Neither experiment licenses RollArt's published training-speed claim for this project.

The controlled throughput comparison used four scripted suffixes, one common read/import-check prefix, one verifier worker per episode, two repetitions per condition, and the same locally cached image. Median wall time was **14.742 s cold serial**, **14.197 s shared-prefix serial**, **8.409 s cold parallel**, and **8.559 s shared-prefix parallel**. Shared-prefix reuse reduced serial time about **3.7%** on this short-prefix fixture, but was about **1.8% slower** than ordinary parallel episodes. Parallel execution was the substantial effect; sharing did not improve this parallel workload. An APFS file-copy microbenchmark on the 69-file source was **13.3 ms** median for `copytree` versus **14.1 ms** for clonefile-based copying over 20 alternating pairs. The small source is below the scale where clone-on-write necessarily helps. These timings exclude policy inference and gradient updates and have too few repetitions for a general training-speed claim. The benchmark script records exact per-run results and verifies equal rewards across conditions.

## A concrete third track to test

Build a **real-workflow RL track** around reversible, inspectable work on versioned public software repositories and timestamped public datasets. An episode specifies a task, allowed tools, initial state, time/resource budget, and an independent verifier. The agent can inspect files or data, search documentation, run bounded tests or queries, modify only its isolated workspace when the task permits, and submit a final artifact. A verifier that the agent cannot edit checks the result against held-out tests or reference computations. This gives immediate feedback for a training loop while preserving a separate prospective forecasting track for delayed real-world truth.

Start with repository repair, then investigate a second family without promising arbitrary real-world action:

1. **Repository repair:** a pinned repository revision, a reproducible failure, isolated filesystem, tests visible during interaction, and hidden regression tests at grading. The terminal reward is test-based success plus a separately reported validity/coverage record. Tests can be incomplete or gamed, so holdout checks and review of reward failures are part of the environment contract.
2. **Data-workflow investigation:** a frozen real dataset and executable question, bounded queries/analysis, then a numeric or structured final answer checked by an independently computed result. [WhatWorkedBench](https://arxiv.org/abs/2609.27490), first posted 2026-09-23, is a nearby research example: its agent chooses measurements on actual workflow code and predicts the effects of configuration changes, while exhaustive CPU runs provide a reference response surface. It reports evaluation of experimental understanding, **not** an RL training speedup. Its method suggests tasks in which an agent spends a limited measurement budget before making a verifiable final prediction.

Both families should record dataset/repository license, source revision, environment image or sandbox definition, verifier revision, task cluster, tool outputs, and final artifact hashes. Train/dev/test must be separated by repository or data source and by task family where feasible, not merely by paraphrased prompts. A held-out test must be unavailable to the agent during the episode. The same trace schema can serve all three tracks, with `reward_available_at`, `verifier_kind`, `source_snapshot_id`, and `policy_revision` making feedback timing and provenance explicit.

The project now implements a separate task contract, Docker coding adapter, and experimental QEMU/HVF coding adapter. It includes a synthetic smoke task and two pinned, public, already-solved Python repository repair fixtures: [Boltons](../examples/realworld_boltons26/README.md) runs through Docker and QEMU/HVF, while [Humanize](../examples/realworld_humanize/README.md) has a generic Docker-adapter smoke. They validate task portability and reward separation, not performance on a held-out repository distribution. Independent held-out repository tasks and the data-workflow adapter remain future integrations. Neither the cited sandbox papers nor these integration tasks demonstrate an improvement to a forecasting policy. Transfer between real-workflow practice and forecasting must be measured, not assumed.

[Branching Policy Optimization](https://arxiv.org/html/2607.14171) (2026-07-15) is a more direct algorithmic reason to preserve branch lineage: it compares returns from sibling suffixes beginning at the same intermediate sandbox state. Its preprint reports 3.6–6.1 absolute-point task-success gains over selected baselines at matched compute in WebShop, ALFWorld, and SWE-bench Verified. Our [branch-local preparation](BRANCH_ADVANTAGES.md) implements only complete-cohort validation and leave-one-out suffix advantages. It deliberately does not assign that local contrast to the identical shared prefix, select branch points from model entropy, or optimize model weights. There is no measured sample-efficiency or RL training-speed gain in this project.

## Training-speed choices in priority order

1. **Instrument the full critical path.** For each episode, record queue wait, environment setup/reset, model prefill/decode, external tool wait, verifier time, reward wait, optimizer time, and weight synchronization. Record p50/p95 latency, completed valid episodes per hour, generated and trained tokens, GPU/CPU utilization where available, and cost. Forecasting needs a separate `forecast_to_resolution` clock; no infrastructure speedup can reduce it below the event's actual occurrence.
2. **Increase useful independent feedback.** Prefer many distinct verifiable real-workflow tasks over repeated rollouts on one task. For forecasting, collect independent short-horizon events in parallel and retain pending labels. [Future-as-Label](https://arxiv.org/abs/2601.06336), 2026-01-09, reports forecasting gains from temporally masked historical events; such data can warm-start research, but historical evidence must truly be limited to the original cutoff and final claims need a fresh live holdout.
3. **Make agent execution and training separate services only at the necessary boundary.** [Agent Lightning v1.0](https://arxiv.org/abs/2608.17528), 2026-08-18, and its [official repository](https://github.com/microsoft/agent-lightning) show a harness-owned tool loop, a model-call proxy, and a trainer that consumes exact request/response trajectories. The authors report a coding-agent gain from 41.8% to 56.4% SWE-bench Verified with 6,000 training examples; that is not evidence of a forecast gain. A gateway around this project's runner is a plausible integration after a trainable policy is chosen. The current text export is not a tokenized training batch.
4. **Use asynchronous collection only with an explicit stale-policy rule.** [AReaL](https://arxiv.org/abs/2505.24298), first posted 2025-05-30 and revised 2026-03-02, reports up to **2.77x** training speedup over synchronous baselines on math/code with the same GPU budget by decoupling rollout and optimization. Its data-staleness controls are essential to that result. Preserve behavior token log probabilities, immutable policy versions, and context/action masks before relaxing the current exact-revision gate. Calendar age is not a substitute for policy-distance measurement.
5. **Test an optimizer suited to single real episodes.** [SAO](https://arxiv.org/abs/2607.07508), 2026-07-08, replaces per-prompt groups with one rollout and a trained value model, using rollout token probabilities and strict two-sided ratio masking. Its experiments cover coding/reasoning and simulated online preference change, not live future outcomes. [SAPO](https://arxiv.org/abs/2608.19842), 2026-08-20, shares actor/value backbone and reports **33.2% lower per-iteration runtime than PPO** on ALFWorld/WebShop; it provides an alternative turn-level credit design but needs its own reproduction. Keep grouped RLOO/no-standard-deviation scaling as the forecast comparison and compare any one-rollout method on matched event and token budgets.
6. **Optimize long trajectories only when they become the bottleneck.** [WAR](https://arxiv.org/abs/2607.17299), 2026-07-19, reports **1.4-1.6x rollout throughput** on long-context agentic tasks through suffix reuse and cache-aware scheduling. [psRL](https://arxiv.org/abs/2608.25683), 2026-08-26, reports up to **5.2x training throughput** from shared prefixes on production traces, with source code still promised in its abstract. These are candidates after measurements show long-context generation or optimizer update dominates. They are not end-to-end gains for this project's short episodes.

For probability forecasting, retain a strictly proper outcome reward. The [2026-09-09 revision of *How Proper Scoring Rules Shape LLM Forecasting*](https://arxiv.org/html/2608.28482v2) found different score and calibration profiles after Brier versus log-score training on historical binary events. It also found materially different realized token counts despite matching rollout and step budgets. Compare Brier, log loss, calibration, and actual tokens/time. Its targeted three-seed replication does not establish a universal best reward or any improvement from adding process-style bonuses. Keep tool-use quality and resource use as diagnostics or separately registered objectives until their effect on held-out outcomes is known.

## Small validation ladder

1. **Contract test:** two pinned repository tasks and two frozen data tasks, each with distinct train and held-out variants. Verify independent setup, reset, deterministic grading, trace provenance, reward delay fields, and no cross-episode state carryover. A scripted agent is enough for this test; it demonstrates environment correctness, not learning.
2. **Latency test:** run the same task suite serially and with a small concurrent worker pool. Report a per-stage profile and compare valid episodes/hour and p95 latency. Add snapshotting, caching, or a different sandbox only if the measured stage warrants it; verify that a reset restores both file and process-visible state.
3. **Learning test:** with a genuinely trainable policy, matched task/token budgets, multiple seeds, and disjoint held-out source clusters, compare no-training, outcome-only grouped baseline, and one chosen single-rollout/turn-aware method. Report success, verifier coverage, invalid rate, tokens, wall time, and train/test gap. For the forecasting track, additionally report raw Brier, baseline improvement, calibration, resolution coverage, and time from forecast to reward.
4. **Transfer test:** train on the new real-workflow track, then evaluate on unchanged future forecasting and other real-workflow holdouts. Any cross-track benefit is a measured outcome; task-specific improvement alone does not establish general agent improvement.

This order yields a usable third environment before taking on a large training system. The strongest immediate acceleration is to obtain more **genuine, quickly verifiable tasks** and remove measured waiting in their execution loop. Live future prediction remains a separate prospective claim with an irreducible real-world clock.

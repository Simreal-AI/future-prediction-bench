# Read-only ext4 plus overlay workspace preparation

[`benchmark_workspace_overlay_ab.py`](../examples/realworld_boltons26/benchmark_workspace_overlay_ab.py)
compares two ways to prepare an independent workspace inside **one already
booted ARM64 QEMU/HVF guest**. The first extracts a prebuilt uncompressed tar
of the pinned Boltons 26.0.0 repository into a fresh tmpfs directory. The
second mounts a fresh overlay with a tmpfs upper/work pair over the same
ext4 repository, exposed through a verified read-only bind. The lower is
**ext4, not EROFS**.

The guest performs two excluded warmups, then 20 matched pairs in alternating
AB/BA order. The timer starts before per-attempt directory creation and stops
when the workspace is ready. The tree digest, scripted repair, function
execution, and cleanup run outside the timed interval. The repair changes the
known `singularize("glass")` output from `"glas"` to `"glass"`; every attempt
checks both behaviors, the same seed tree digest, the same repaired source
digest, an unchanged read-only lower, and complete cleanup. This is a public,
already-solved integration fixture rather than held-out agent evaluation.

The [path-free 20-pair report](measurements/workspace_overlay_ab_2026-09-25.json)
was generated by the public scripts. Its SHA-256 is
`420ee03851a76e03c04e04160b8351ec20fc94be9f28a87d06592b25f28192d6`.

| Guest-clock workspace preparation | Tar extraction | ext4 + overlay |
| --- | ---: | ---: |
| Median, 20 measured attempts per arm | 4.517 ms | 0.0703 ms |
| p95, nearest rank | 4.691 ms | 0.0875 ms |

Overlay preparation was faster in all 20 matched pairs. The ratio of arm
medians is **64.3× for workspace preparation only**. The seed is small: 69
files containing 852,065 bytes; the uncompressed tar is 983,040 bytes. The
two excluded warmups mean that these are warm-cache results. Neither the
ratio nor the sub-millisecond overlay setup is a whole-episode speedup, a VM
checkpoint/restore result, or an RL training throughput measurement.
Tar extracts all 69 files before the workspace is ready, whereas OverlayFS
exposes the lower tree immediately and can defer copying a file until its
first write ([Linux OverlayFS documentation](https://docs.kernel.org/filesystems/overlayfs.html)).
That later copy-up cost may move into action or grading time. The read-only
bind here is a mount view controlled by trusted guest root, not an EROFS
image or an immutable boundary against malicious guest root.

The report separates one-time guest setup: 0.032 ms for the read-only bind,
0.021 ms for scratch tmpfs mount, 6.001 ms for the seed tree digest, and
4.323 ms for tar creation. Host-side disk clone, VM boot, and guest script
upload took 0.001 s, 5.521 s, and 0.143 s. The host-observed guest call,
which includes setup, all attempts, validation, and cleanup, took 0.675 s.
Physical write bytes are omitted because tmpfs and overlay metadata writes
could not be separately attributed. Repository payload and archive sizes are
descriptors, not measured physical I/O.

To reproduce, first create the pinned v2 task and asset directory using the
[bounded-edit setup guide](SMALL_EDIT_MICROVM.md). That guide in turn links
to the [microVM asset builder](MICROVM_ENV.md). The generated directories
remain outside the release source, under ignored `runs/`. Then run:

```sh
python3 -m examples.realworld_boltons26.benchmark_workspace_overlay_ab \
  --task-dir runs/boltons-v2-task \
  --assets-dir runs/boltons-v2-assets \
  --output runs/boltons-workspace-overlay-ab \
  --pairs 20
```

The host runner verifies the task's seed digest, source file, asset manifest,
and qcow2 digest, then uploads the [self-contained guest program](../examples/realworld_boltons26/workspace_overlay_ab_guest.py)
with a SHA-256 check. It rejects missing pairs, changed arm order, failed
isolation checks, and inconsistent timing summaries. The VM has no network
interface. The experiment does not run model inference, hidden grading, reward
calculation, policy optimization, or a per-attempt microVM sandbox.

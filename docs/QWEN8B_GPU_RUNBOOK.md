# Qwen3-8B GPU validation runbook

**Status:** planned, not run. This project has no measured Qwen GPU rollout, optimizer update, or end-to-end RL training result. Its current [training preparation](RL_TRAINING.md) and [trajectory control plane](../future_prediction_bench/trajectory_control.py) export `trainer_ready=false`: they do not yet produce tokenizer-aligned behavior log probabilities or change model weights. API-driven or scripted actor tests can validate environment scheduling, but cannot substitute for open-weight training measurements.

## Model and resource envelope

Use the official [Qwen/Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B) text model for the first GPU experiment. Pin a model repository commit, tokenizer/chat-template commit, framework/container versions, BF16 precision, and Qwen's thinking-mode setting for every arm. The [official configuration](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json) has about 8.2 billion parameters, 36 layers, eight KV heads, and 128 dimensions per head. BF16 weights alone are approximately 15.3 GiB. A BF16 KV cache is approximately `2 × 36 × 8 × 128 × 2 = 147,456` bytes per token: 0.5625 GiB at 4,096 tokens and 4.5 GiB at 32,768 tokens **per active sequence**, before runtime, batching, and training activations.

The following are engineering **estimates, not tested minimum requirements**. Confirm them with a memory probe on the selected hardware before committing to a run.

| Stage | Short-context feasibility budget | Recommended first comparison | Boundaries |
| --- | --- | --- | --- |
| Frozen inference and sampled-token log probabilities | One 24 GB GPU, at most 4K context and very low concurrency | One 48–80 GB GPU | 32K context or several simultaneous conversations can exceed the small-card budget. |
| BF16 LoRA optimizer update, alternating with rollout | One 48 GB GPU with gradient checkpointing, short sequences, and no separately loaded KL reference | One 80 GB GPU for the initial 4–8K pilot | A 24 GB, 4-bit QLoRA attempt is a separate precision ablation; it must not be represented as the BF16 comparison. |
| Concurrent, disaggregated rollout and LoRA update | Two GPUs: approximately 24 GB for inference plus 48 GB for training at short context and low concurrency | Same-node 2 × 80 GB GPUs, one inference GPU and one training GPU, with CPU environment workers | Long coding histories may require larger cards, sharding, or shorter declared horizons. Measure memory and truncation before scaling. |

The current [microVM adapter](MICROVM_ENV.md) launches an ARM64 Linux guest through QEMU/HVF on Apple Silicon. It cannot be moved unchanged to a typical NVIDIA Linux/KVM host. A GPU experiment must either keep that Mac as a remote CPU environment and include network time in its results, or implement and verify a Linux/KVM guest path first. Merely moving the model to a GPU does not accelerate the existing VM checkpoint operation.

## Offline GPU-job input preflight

Run `python -m future_prediction_bench.gpu_preflight --plan /absolute/path/to/plan.json --output /absolute/path/to/preflight-report.json` before reserving a GPU. The command uses only Python's standard library and local files; exit code `2` blocks an invalid input contract. The `qwen8b-gpu-job-preflight-0.1` plan has exactly six top-level fields: `schema_version`, `model`, `runtime`, `dataset`, `rollouts`, and `trainer`. Every local file reference is a relative `{"path": "...", "sha256": "<64 lowercase hex>"}` pair, resolved under the plan's directory. The source of truth for the exact field-level schema is [gpu_preflight.py](../future_prediction_bench/gpu_preflight.py), with runnable positive and rejection cases in [test_gpu_preflight.py](../tests/test_gpu_preflight.py).

The audit requires a 40-character Qwen3-8B model commit and matching tokenizer commit, hash-bound `config.json` and `tokenizer_config.json`, the chat-template hash, and an explicit `enable_thinking` value. It checks Qwen3-8B's architecture fields, BF16 model precision, a pinned vLLM version of at least `0.8.5` and container digest, native context bounds, and `processed_logprobs`. The latter is the [TRL vLLM integration's](https://huggingface.co/docs/trl/vllm_integration) documented mode for log probabilities after sampling transformations; raw model logits are a different quantity. Qwen's [model card](https://huggingface.co/Qwen/Qwen3-8B) documents the thinking-mode switch, native 32,768-token context, and vLLM minimum. Pin the actual official snapshot with a trusted Hub download before creating this plan; matching local JSON fields and self-declared commit strings alone do not authenticate model weights.

The coding data contract requires separate SHA-bound train and development manifests with source-commit, source-archive, verifier, environment-image, license, repository, and task-cluster identities. Declared task, cluster, repository, source-commit, and source-archive identities must not overlap across splits; public solved fixtures are rejected as training data. Repository URLs use HTTPS; the audit normalizes host case, the default port, GitHub's `www` alias, path case and an optional `.git` suffix, and rejects encoded or ambiguous paths. A sampled-token export must bind the train manifest hash and source commit for each task, contain complete same-policy groups, preserve generated token IDs and assistant-only masks, and supply finite chosen-token behavior and teacher-forced log probabilities for every policy token. Context/tool-output positions must have no policy loss. The audit rejects stale policy revisions, truncation, incomplete groups, missing likelihoods, and a maximum served-versus-replayed token log-probability difference over `0.05`. This is a structural and numerical check of supplied values, **not** proof that those values came from the stated weights. Current text-only `prepared_groups.json` exports fail this gate by design.

The trainer section must pin TRL and an entrypoint file hash, specify `grpo` with a finite learning rate and positive step budget, set the generating policy revision and zero permitted lag, and declare an AdamW optimizer, `scale_rewards="none"`, and `loss_type="dr_grpo"`. These last two choices follow [TRL's GRPO controls](https://huggingface.co/docs/trl/grpo_trainer), but this audit cannot inspect Python semantics or run an optimizer. Even when `input_contract_passed=true`, the report **always** says `trainer_ready=false`, `gpu_executed=false`, and `optimizer_update_observed=false`. Only a later GPU smoke with trusted model snapshot, prefix-preserving tool-call template, observed likelihood provenance, finite gradients, actual optimizer steps, and changed/reloadable adapter weights can establish trainer readiness. [TRL's OpenEnv integration](https://huggingface.co/docs/trl/openenv) is a potential future connection for interactive rollouts; it is not implemented here.

## Gates before any training claim

1. Freeze a multi-repository coding-task manifest with image, source, verifier and task hashes, disjoint train/development/test repository families, action budgets, and a hidden verifier the actor cannot read. The two existing solved public repository fixtures, Boltons and Humanize, have both been exercised in the microVM path and are useful for plumbing and reward-parity checks, not generalization. For forecasting, use prospective event-cluster splits and wait for authentic outcomes; a GPU cannot shorten settlement time.
2. Implement the Qwen actor and exact tokenizer/chat-template mapping for every assistant turn and tool call. Save sampled token IDs, assistant-only loss masks, chosen-token behavior log probabilities under the **actual generating policy revision**, decoding settings, and immutable observation times. Tool output remains context, not a policy target. On a fixed transcript probe, compare served and teacher-forced token likelihoods and report the distribution of differences; reject malformed alignment, missing values, or unaccounted truncation. Keep `trainer_ready=false` until this gate is demonstrated.
3. Run a small real-model smoke test: 16–32 graded coding episodes and at least ten LoRA optimizer updates. Show finite loss and gradients, changed adapter hash, saved/reloaded adapter behavior, reward and isolation parity, and no verifier leakage. This establishes working training plumbing, not a quality gain.
4. Only after these gates, compare algorithms and systems on enough independent held-out tasks for an interpretable interval, using at least three training seeds. Report improvement against the frozen pretraining model, not only rising train reward.

The first optimizer control should use the same proper outcome reward and grouped samples as the project's existing [RLOO preparation](RL_TRAINING.md). In [TRL's documented GRPO configuration](https://huggingface.co/docs/trl/grpo_trainer), `scale_rewards="none"` removes within-group standard-deviation scaling, and `loss_type="dr_grpo"` is a separate choice that removes sequence-length normalization. A fixed-size RLOO advantage is `G/(G−1)` times the mean-centered advantage; account for that scale in a learning-rate comparison. Compare with standard group-scaled GRPO under the same task, model, token, update and GPU-hour budgets. This is especially relevant to stochastic forecasts because [Uncalibrated Reasoning](https://arxiv.org/abs/2508.11800) reports overconfidence from standard GRPO, whereas a recent [proper-scoring-rule forecasting study](https://arxiv.org/abs/2608.28482) directly evaluates Brier-trained models. Neither finding proves a winner on this project's data.

Next test sequence-level importance ratios motivated by the [Qwen GSPO paper](https://arxiv.org/abs/2507.18071), while preserving exact multi-turn generation masks. DAPO-style token aggregation can be a separately declared length-control ablation; do not silently filter all-zero or all-one reward groups after delayed outcomes. [TRL's experimental AsyncGRPO](https://huggingface.co/docs/trl/main/async_grpo_trainer) provides a possible bounded-queue, versioned LoRA-sync starting point, but must be pinned and adapted to this environment. Compare staleness bounds zero and one only after the generating revision and token likelihoods are reliable; log every discarded or masked trajectory. [veRL's LoRA guide](https://verl.readthedocs.io/en/latest/advance/ppo_lora.html) is an alternative integration reference, not evidence that this project already trains with veRL.

## Throughput and quality experiment

Use the same two-GPU allocation, CPU environment hosts, pinned Qwen revision, verifier, tasks, output/context limits, and decoding policy in both arms. Arm A uses a synchronous stage barrier; Arm B overlaps inference, environment interaction, verification, weight transfer and optimizer work with bounded queues. A fixed-trace replay isolates scheduler overhead and reward parity. Real online rollouts then measure whether the overlap remains useful when the model generates actual tool actions. Warm both arms; run at least five paired, order-reversed repetitions on a preregistered task set with verifier-tail strata. Publish raw per-episode records and aggregate intervals, not only a best run.

Primary systems metric: **valid, graded episodes per wall-clock hour**, paired with optimizer updates/hour and GPU-hours per valid episode. Also record generated/processed tokens per second, p50/p95 stage and queue waits, verifier tail, GPU utilization and peak VRAM, transfer bytes/time, environment setup/checkpoint time, accepted versus stale/void/pending counts, and reward distributions. An episode awaiting trustworthy reward is not a completed training sample. A faster rollout queue is not a faster trained model unless the full optimizer loop and held-out quality are measured.

For model quality, report time and GPU-hours to a preregistered held-out target. Coding tasks need task-family-aware success intervals and valid-submission coverage; prediction tasks need event-cluster-aware Brier score, calibration, and outcome coverage. Keep train/test information cutoffs intact. The [RollArt paper](https://arxiv.org/abs/2512.22560) motivates this disaggregated comparison, but its large-cluster speedups are not a speedup claim for this implementation.

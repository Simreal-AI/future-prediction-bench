# MicroVM environment throughput: source audit and next measurements

Evidence checked on **2026-09-25**. This note distinguishes the project's measured QEMU/HVF environment speed from published results on other systems. It addresses the third, quickly verifiable real-world RL track: a model edits a pinned repository in an isolated guest, then an independent host verifier checks the result. It does not claim to accelerate resolution of future events in the prediction track.

## What is actually implemented

| Component | Current mechanism | Important limit |
| --- | --- | --- |
| Full-state coding guest | `MicroVMRuntime` launches a small ARM64 Linux VM with QEMU/HVF on an Apple Silicon host. It has a dedicated writable qcow2 disk, a pinned kernel and initramfs, no virtual NIC, and no host-directory mount. QEMU `savevm` and `loadvm` capture and restore CPU, RAM, device, and writable-disk state, as [QEMU documents](https://www.qemu.org/docs/master/system/images). | This is **QEMU/HVF**, not Firecracker. The path has no measured multi-tenant security guarantee or cross-host snapshot portability. The trusted guest control runs as root; current candidate Python runs as UID/GID 65534 under a [versioned binding](GUEST_IDENTITY_INTEGRITY.md). Earlier timing reports used their original execution contract. |
| Independent sibling VMs | `fork_snapshot()` pauses a warm parent, copies its qcow2 using APFS `clonefile` when available, starts new QEMU processes paused, then `loadvm` restores the common full state into each child. Each child has a separate writable disk. An optional bounded path starts and restores two to four children concurrently. | This is host-controlled **copy plus restore**, not a live hypervisor fork or Daytona's managed remote `sandbox.fork()`. The parallel path has its own matched, graded live measurement below. |
| Reusable full-VM template | `MicroVMTemplate` exports a checksum-bound qcow2 while the parent is paused, then reopens it by exact template ID after that parent exits. It clones separate writable child disks and restores the saved QEMU state with bounded parallel startup. | The one-time template still requires a VM boot/export, and every child still pays QEMU process startup and full-state restore. This is a local analogue of a hot snapshot pool, not in-guest process COW or a hosted service. |
| Guest-local warm branches | Trusted Python/OverlayFS prototypes fork warmed heap and repository state. The [cooperative checkpoint example](../examples/cooperative_guest_checkpoint/README.md) freezes an overlay prefix and forks 100 separately namespaced siblings from ten live templates. A [pinned opt-in `RealWorldEnv` adapter](../examples/cooperative_realworld/README.md) then graded 20 complete repair/baseline episodes against a prepared full-VM child control. | These branches share one guest kernel, require a quiescent single-process worker, and do not survive guest death. The graded adapter is confined to one declared task contract; it is not a general `RealWorldEnv` adapter or secure untrusted-agent sandbox. |
| Bounded task tools | `MicroVMCodingAdapter` exposes file listing, file reading/writing, a fixed visible check, and submit. Trusted host code drives the serial shell; the policy has no general shell action. Hidden expected outputs stay on the host. By default, each hidden case starts by restoring the submitted full-state snapshot. | Operator-selected guest images and policy-edited code still need review. A successful toy fixture is not proof against hostile guest escape or reward hacking. |
| Opt-in stateless hidden cases | An explicit task/verifier/helper binding can select one full-VM restore followed by separate guest mount/PID namespaces and a batched trusted-host verifier call. Process quiescence is checked at the submission boundary. | This is a narrow task-authored contract; cases run in one shared-kernel VM without whole-VM restoration between them. Per-task reward equivalence and isolation must be validated; see [the experiment](STATELESS_VERIFIER.md). |
| Resident guest adapter | An [experimental `RealWorldEnv` adapter](../examples/resident_guest_candidate/README.md) keeps one trusted QEMU guest booted, uses a private mount/PID namespace and overlay per episode, and runs host-authored cases with unprivileged execution and inherited resource caps. Expected outputs and rewards remain on the host. | Proven on one pinned stateless public fixture; no arbitrary dependency cache, hostile guest-root attestation, or full VM C/R per case. Current batch/sequential results are smokes, not a repeated throughput A/B. |
| Cheaper Docker branching | The separate Docker adapter copies bounded workspaces, using APFS `clonefile` where available. Read-only actions skip checkpoints; unchanged workspace hashes reuse a prior one. Branches restart a fresh container. | These are **filesystem-only** snapshots: live processes, `/tmp`, and guest memory do not survive. They are not DeltaBox's process+filesystem checkpoint or Crab's host-side dirty-state inspector. |
| Bounded pipeline | [Trajectory control](ROLLART_CONTROL_PLANE.md) hands multi-turn episodes between bounded actor, environment, and verifier pools, records stage/queue times, and applies a policy-revision freshness gate. | There is no remote environment fleet, GPU prefill/decode placement, weight synchronization, behavior-token log probabilities, or optimizer. The exported text trajectory is not yet trainable. |

The [reproducible Boltons fixture](../examples/realworld_boltons26/microvm_benchmark.py) checks that the unmodified source scores 0, a scripted public repair scores 1 on all 14 host-side cases, and restoring a pristine full-VM snapshot brings back the original bug, a killed guest process, and its RAM state. Its final three paired, alternated timing runs on one development host gave **8.578 s median** for a new disk and cold VM versus **3.324 s median** for reusing an already booted VM and restoring a pristine snapshot: **2.581× steady-state environment-episode throughput** for this fixture, or **1.657×** over three episodes when the one-time 5.890 s warm setup is charged. The [public timing report](measurements/microvm_boltons_v0.6.0.json) is included with source. This remains a developmental single-host measurement until independent reproductions are available.

The separate [two-sibling experiment](../examples/realworld_boltons26/microvm_fork_benchmark.py) compares **parallel cold independent VMs** with independent children reconstructed from a warm parent. Three paired runs gave **15.260 s versus 9.748 s median per two-branch batch**, a **1.565× environment-branch throughput ratio**. Including 6.397 s of parent setup across those three batches gives **1.230×**. Both paths use the same disk clone-or-copy helper; the cold VMs boot in parallel; both conditions retain a live parent during timing. The benchmark confirms disjoint guest RAM and writable-disk markers and scores repaired/untouched siblings `[1, 0]`. Its [sanitized report](measurements/microvm_fork_boltons_v0.6.0.json) and [run protocol](MICROVM_ENV.md) explain the limits. Both experiments use one publicly solved repository, scripted actions, and host grading. They contain **no policy inference, optimizer step, learned-policy improvement, or repository diversity**.

The [full-VM primitive sweep](measurements/microvm_primitives_v0.6.0.json) measures QEMU/HVF HMP `loadvm` medians of 48.13, 51.11, and 81.95 ms at configured 128, 256, and 512 MiB, respectively; the 512 MiB p95 was 244.16 ms. In contrast, the [earlier guest-local COW prototype](measurements/guest_cow_branch_v0.6.0.json) measures a 0.988 ms median and 1.881 ms p95 for mount, fork-to-ready, child reap, and overlay removal inside a prebooted VM. The later [private mount-namespace variant](measurements/guest_mount_namespace_v0.6.0.json) measures 0.864 ms median and 0.990 ms p95 for its complete branch cycle, including namespace creation and cleanup. The former restores a whole VM; the latter two reuse trusted processes and do not provide separate VMs or untrusted-agent containment. The two guest variants also use different prepared assets/program versions, so neither a full-VM nor guest-to-guest speed ratio is controlled.

The full-VM branch path now also runs through `RealWorldEnv`: a [reproducible two-child check](../examples/realworld_boltons26/check_microvm_branch_env.py) saved a checkpoint, made a later parent write, restored two independent children, and graded the public repair and baseline `[1.0, 0.0]` with 14 host-private cases each. RAM and ext4 markers and the repaired source remained separate; the [report](measurements/microvm_realworld_branches_v0.6.0.json) records this correctness run and its sibling-local suffix advantages of `+1/-1` with no shared-prefix credit or model update. Separately, a [three-pair serial-versus-parallel child startup experiment](measurements/microvm_parallel_fork_boltons_v0.6.0.json) reduced median child start/restore from 0.679 to 0.490 s, but median whole two-branch graded batch only from 7.694 to 7.252 s (1.061×). A [four-sibling reusable-template comparison](measurements/microvm_template_four_siblings_v0.6.0.json) measured 15.063 s median for parallel cold VMs versus 11.532 s for independently restored template children (1.306×), or 1.125× after its one-time template setup. On this 8-GB host, fan-out benefits shrank at four siblings. Neither experiment includes an agent model or optimizer.

An [exact-contract stateless verifier experiment](STATELESS_VERIFIER.md) attacks the larger repeated-grading cost without changing the general full-VM adapter. Its pinned task declares that cases need no shared filesystem writes or live process state; each case receives its own mount and PID namespace within one guest, an overlay/tmpfs view, and unprivileged Python execution, while expected outputs stay on the host. Seven rotated real-guest comparisons with exact per-case output parity gave **5.433×** median 14-case grading-stage throughput against full-VM restore per case. In six alternating full `RealWorldEnv` repair episodes, the measured ratio was **1.152×** because boot, helper upload, and actions remain. The helper is not a DeltaBox process snapshot and is valid only for task-authored, quiescent stateless cases.

An [immutable-template experiment](../examples/realworld_boltons26/microvm_template_benchmark.py) exported the warm snapshot once, closed the parent, and spawned two independent children from the persisted template. Both children inherited pre-export RAM and excluded later parent writes; repaired/baseline rewards and 14-case grading were unchanged. Across two alternating pairs, median cold-parallel versus template two-branch batches were 10.933 versus 6.273 s (1.743×); charging 6.126 s template setup across both batches reduced the ratio to 1.171×. The [sanitized report](measurements/microvm_template_boltons_v0.6.0.json) includes each run. This is parent-free reuse of a *whole VM snapshot*, not DeltaBox's process-template fork, and the two-pair sample is too small for a stable tail claim.

## Six systems, at their real state boundaries

### DeltaBox: process-level branching inside a VM

**State and restore.** [DeltaBox v2 (2026-06-08)](https://arxiv.org/html/2605.22781) couples two pieces that ordinary VM snapshots treat together: a modified Linux 6.8 OverlayFS implementation freezes the current writable layer and switches to a new one, while DeltaCR uses CRIU dumps and a pool of frozen process templates. A restore switches the filesystem layer and forks the relevant process from a warm template; an evicted template falls back to a slower CRIU restore. Its StateManager couples these components so file and process state refer to one logical checkpoint. It can therefore roll back one agent process while other agents inside the **same** VM continue. Its deployment uses Firecracker for the VM boundary, an in-guest daemon for latency-sensitive checkpoint work, and a host controller for coordination. This is not a drop-in QEMU monitor command. [Architecture and deployment](https://arxiv.org/html/2605.22781).

**Isolation and measurement.** Firecracker isolates one VM from other VMs; agents co-located inside a DeltaBox VM share its guest kernel and read-only base. The paper's VM has 4 vCPUs and 8 GiB RAM; the main machine has 96 physical cores, 760 GiB RAM, and NVMe storage, with four 96 GiB GPUs additionally used for RL fan-out. On event-weighted SWE-bench MCTS trajectory replays, Table 2 reports **10.83 ms mean checkpoint blocking** and **1.86 ms mean restore blocking**. The checkpoint number is API call-to-return time **excluding completion of an asynchronous CRIU dump**, which is intended to overlap the LLM wait. Some earlier abstract text reports 14/5 ms; use the latest v2 table and its stated denominator for comparison. Neither number is a full RL step or a macOS/HVF result. [Experimental setup and Table 2](https://arxiv.org/html/2605.22781). The [authors' project repository](https://github.com/dongyunpeng-sjtu/deltabox/blob/main/README.md) says the kernel patch, controller, and benchmark artifacts are not yet public, so independent implementation-level replication is currently limited.

**Transfer experiment and result.** The two- and four-sibling QEMU comparisons use pinned assets and preserve independent full VM state. A separate [cooperative in-guest process/OverlayFS prototype](../examples/cooperative_guest_checkpoint/README.md) established ten template checkpoints and 100 sibling restores in one real VM, with a **0.470 ms** median ready time, a **1.026 ms** median no-case branch cycle, exact heap/prefix/source isolation, unchanged outer workspace, and correct host-compared rewards on two branches. The [graded RealWorldEnv integration](../examples/cooperative_realworld/README.md) subsequently ran 10 matched repair/baseline pairs against a prepared full-VM control, with exact common action, all 14 per-case, and reward parity. Complete graded-episode medians were **0.810/1.647 s** including teardown; setup-amortized totals for 10 episodes per arm were **14.917/23.315 s**. The cooperative path shares a guest kernel and is limited to a pinned, quiescent contract; these results are not transparent arbitrary-process DeltaBox, same-contract full-VM restore, or model-training throughput.

### Crab: decide *whether* and *what* to checkpoint

**State and restore.** [Crab (2026-04-30)](https://arxiv.org/html/2604.28138) interposes an HTTP proxy on agent-to-LLM calls to infer turn boundaries and retain conversation state. A Linux eBPF monitor and cgroup/soft-dirty tracking detect net filesystem and persistent process/memory changes since the last checkpoint. The decision has four cases: skip, filesystem only, process only, or both. Its backend uses OpenZFS for file state and runc/CRIU for processes; a transactional manifest points to the newest compatible `(process, filesystem)` artifacts so a partially completed checkpoint is never restored. The proxy runs checkpoint work during the subsequent LLM wait and delays the next turn if it has not finished. This is a **host-side selective C/R policy**, not a faster VM snapshot algorithm. [Inspector and manifest design](https://arxiv.org/html/2604.28138).

**Isolation and measurement.** Crab's tested implementation uses host-visible Linux sandbox processes with runc/CRIU and OpenZFS. The paper discusses containers and microVMs as agent sandbox types, but its eBPF/cgroup inspector and CRIU backend are not shown working across our macOS-to-Linux-guest boundary. On an AWS c6id.32xlarge (128 Xeon cores, 256 GiB RAM, four NVMe drives), the authors replayed 100 *already-solvable* tasks per benchmark/agent with one injected crash, across 16–96 co-located sandboxes. The reported **100% recovery correctness** applies to those task criteria (full sandbox state for Terminal-Bench, final patch for SWE-bench); skip rate reaches **up to 87% of turns** and end-to-end completion stays within **0–1.9% of the no-fault run** in that setup. On 2,063 manually labeled turns, their inspector had zero false negatives. These are crash-recovery and checkpoint-traffic measurements, not a policy-learning gain. [Evaluation setup and results](https://arxiv.org/html/2604.28138).

**Transfer experiments and results.** The [conservative turn-aligned journal](SEMANTIC_VM_RECOVERY.md) compares every-turn against read/list skipping while probing guest files and processes, injecting an orphan snapshot, killing the real QEMU process, and checking restored RAM/live-process state and exact reward. The current four-arm run skipped three of eight saves with exact case parity and resumed terminal verification after an injected hidden-case interruption on the same live adapter; paired runs changed whole-episode timing direction. A separate [asynchronous QEMU checkpoint gate](ASYNC_VM_CHECKPOINT.md) runs the same full `savevm`/fsynced manifest during a simulated policy wait and blocks the next action and terminal reward until publication. In current two AB/BA pairs with 100 ms wait per turn it exposed 0.006826 s of gate wait over six turns, whereas a zero-wait control exposed 0.528095 s; whole graded-episode deltas remained variable. Neither path has Crab's eBPF/cgroup/soft-dirty inspector, ZFS/CRIU, host-wide scheduler, or agent conversation recovery. These are two separately measured transfers of its checkpoint-selection and wait-overlap ideas, not a Crab replication.

### SWE-MiniSandbox: fresh lightweight Linux task environments

**State and restore.** [SWE-MiniSandbox v5 (2026-05-30)](https://arxiv.org/html/2602.11210) creates a private task directory and terminal session, a per-instance Linux mount namespace, `chroot`, bind mounts, and a cached Python `venv` built against shared interpreter installations. It reuses prepared dependencies and materializes a **fresh workspace per attempt**. It does not checkpoint or restore live process/RAM state for branching. The [official implementation](https://github.com/lblankl/SWE-MiniSandbox) exposes this as a Linux-only alternative to one container per task.

**Isolation and measurement.** This is shared-kernel namespace isolation, lighter than a VM; the paper itself says it is less suitable for potentially malicious code or kernel-level tasks. On a node with eight B200 GPUs, 184 CPU cores, and an 800 GB SSD, the authors capped the MiniSandbox comparison to 32 CPU cores against their Docker server and ran 128 environments per RL update. Reported cached storage is **13.5 GB vs 295 GB (about 5%) on SWE-smith**, but **89 GB vs 605 GB (about 15%) on SWE-bench Verified**. One reported per-instance preparation comparison is **23.62 s vs 88.86 s (about 27%)**, not an end-to-end training speedup. Official-container evaluation was used for the main learned-model results; their alternative verifier needed documented special-case handling on some instances. [Setup, tables, and limits](https://arxiv.org/html/2602.11210).

**Transfer experiment and result.** The [guest mount-namespace prototype](GUEST_MOUNT_NAMESPACE.md) demonstrates a private mount view and tmpfs/overlay repository layer *inside* Linux with a 200-cycle latency/separation check. The newer [resident adapter](../examples/resident_guest_candidate/README.md) adds a bounded `RealWorldEnv` action protocol, host-private grading, batch/sequential case transport, and CPU/address-space/process/file/FD limits on unprivileged case code. Its real-VM checks include reward parity, cross-case isolation, ordinary timeouts, and a scored file-size-limit violation; they remain single-run smokes on one repository. It does not implement MiniSandbox's cached multi-repository dependencies, full arbitrary task runner, or paper percentages. A matched next experiment should compare checksum-pinned dependency preparation across multiple repositories under fixed isolation and reward contracts. Arbitrary generated code in a shared guest kernel still needs a stronger security assessment.

### RollArt: scheduling trajectories, not checkpointing guest OS state

**State and restore.** [RollArt v2 (2026-06-15)](https://arxiv.org/html/2512.22560) keeps each trajectory's observation/action history in an EnvManager and lets generation, CPU environment interaction, and reward scoring proceed independently. It routes prefill-heavy and decode-heavy domains to different GPU classes and sends stateless rewards to serverless workers. At a weight update it suspends new generation, updates inference weights, **recomputes in-flight KV caches**, resumes rollouts, and aborts trajectories beyond its bounded policy-version age. It does **not** claim a filesystem, process, or VM rollback primitive. Environment execution is on containerized CPU clusters; RollArt's contribution is a distributed training control/data plane, not a new isolation boundary. [Control plane](https://arxiv.org/html/2512.22560).

**Measurement.** The paper's research setup uses 96 H800 and 32 H20 GPUs, dedicated CPU environment clusters, and a serverless reward platform; its baselines use 128 H800 GPUs, a different hardware mix. It trains Qwen3 8B–32B models with GRPO, batch 512 and group 8. It reports mean RL step time over five iterations, token throughput per step, and time to a target validation score of 0.85 on Qwen3-32B. In its Figure 10 discussion, the authors report **2.05×, 1.35×, and 1.31× shorter step times** than their Sync+, One-off, and reimplemented AReaL baselines, respectively. These are not snapshot latencies and cannot be multiplied by our VM reuse ratios. [Evaluation setup and comparison](https://arxiv.org/html/2512.22560).

**Transfer experiment and result.** The [same-host trajectory control pilot](ROLLART_CONTROL_PLANE.md) replays fixed multi-turn coding episodes through bounded actor/environment/reward queues under 0/2/5-second verifier delays. Two alternating repetitions with two reward workers and two live slots measured **1.638×, 1.568×, and 1.575×** valid graded episode throughput relative to equal-resource serial execution, with exact rewards and host-evidence digests. A one-reward-worker/four-slot configuration regressed to **0.951×** at the 2-second delay. A separate nine-pair experiment moved a short verifier-readiness wait out of reward workers but found **no complete-batch speed gain**: ratios were 0.935×, 0.946×, and 0.938× under 0/2/5-second delays because reward queue waits often hid the delay already. This tests scheduling of scripted environment collection, not RollArt GPU training speed. Actual model generation, behavior probabilities, optimizer updates, and synchronized weights remain absent.

### Collinear Simulation Lab: task worlds and verifier contracts

**State and restore.** [Collinear's official sandbox documentation](https://docs.collinear.ai/core-concepts/sandbox) says each rollout gets a fresh workspace with its own Docker network and containers; seed data is reapplied and the workspace is torn down afterward. Local runs use Docker Compose, while a remote mode uses **Daytona**. Its [tool protocol](https://docs.collinear.ai/api-reference/tool-server-protocol) presents simulated services through `/tools` and `/step`. State changes are tracked as before/after **application-state diffs** after mutating calls, and programmatic or rubric-based verifiers consume rollout artifacts. These logical snapshots are for inspection and scoring, not evidence of OS process/RAM checkpointing. [State diffs](https://docs.collinear.ai/simulation-lab/understanding-results), [verifiers](https://docs.collinear.ai/simulation-lab/verifiers-and-reward-models).

**Isolation and measurement.** The documented boundary is a separate Docker network/container workspace per rollout, not a claim that every task is a VM. Its public docs describe clean seeded runs and repeatable scoring but do **not** publish a controlled host specification, checkpoint latency, or comparable training-throughput benchmark. Its simulated user and enterprise-tool behavior is useful for practice, yet remains a model of real workflows; it is not direct verification of a public repository fix or a future event. Collinear remote execution may itself use Daytona, so counting their product claims as two independent speedups would be wrong. [Product overview](https://docs.collinear.ai/simulation-lab/overview), [sandbox modes](https://docs.collinear.ai/core-concepts/sandbox).

**Transfer experiment and result.** The [seeded CI-triage world](COLLINEAR_CI_TRIAGE.md) implements an in-process tool-discovery/step protocol, fresh per-rollout SQLite state, before/after row diffs, and a host-only exact-state verifier. Thirty alternating pairs retained identical initial/final state and reward while prepared-seed copies reduced median complete graded simulated episodes from **11.114 to 9.088 ms** (1.234× ratio of summed episode times, or 1.224× charging one seed build). Five text-only, forged, wrong-order, overbroad, and wrong-branch traces received no false reward. This is a local simulated workflow without Collinear's service, Docker/Daytona isolation, model inference, or training; its timing cannot be used as a real-world repository or VM speed claim.

### Daytona: hosted cold/hot snapshots and independent VM forks

**State and restore.** [Daytona's persistence documentation](https://www.daytona.io/docs/en/persistence/) distinguishes **cold snapshots** (filesystem only), **hot VM snapshots** (filesystem plus memory/process state), and **forks** (a new independent VM containing the running parent's filesystem and memory). Container sandboxes cannot hot-snapshot or fork live memory; the VM class can. Unlike our host-owned QEMU qcow2 clone plus `loadvm`, Daytona provides a managed sandbox API, persistent lineage, and warm pools. Its [isolation documentation](https://www.daytona.io/docs/en/isolation/) describes distinct container and VM classes with separate resource and network controls. Outbound network defaults depend on account tier, so a comparable no-network test would need an explicit block-all setting.

**Measurement.** In Daytona's own [HUD RL coding guide](https://www.daytona.io/docs/en/guides/reinforcement-learning/hud-rl-cookbook/), a small 1-vCPU/1-GiB/3-GB task has about **74 s one-time image/snapshot build**, about **3 s cold create-to-usable**, **0.66 s fork operation**, and **1.78 s median fork-to-usable graded rollout**. The 8/32/128/256-way create ladder reports p50 usable times of 2.8/3.3/5.1/9.9 s, medians of three repetitions. These are vendor measurements from the SDK boundary, including its tunnel/server readiness, on a different workload and platform from our Boltons/QEMU timings. The guide does not establish a universal hosted-vs-local speedup.

**Transfer experiment.** Our existing paired two-sibling test is the local analogue: it compares independently live QEMU children with independently live cold VMs and checks RAM/disk isolation and reward parity. The completed four-sibling comparison remains small; repeat it with more alternating pairs to estimate p95 and record setup, grading, and amortized throughput. If a hosted provider is later evaluated, repeat the **same guest workload, no-network policy, verifier, branch count, and measured SDK boundary** there; an unmatched Daytona guide number is not a valid baseline.

These six systems optimize different units: DeltaBox a **checkpoint/restore event**, Crab **checkpoint selection and crash recovery**, MiniSandbox **environment preparation and storage**, RollArt **training pipeline wall time**, Collinear **task-world and verifier production**, and Daytona **hosted sandbox lifecycle and fan-out**. [QEMU's snapshot specification](https://www.qemu.org/docs/master/system/images) says `savevm` includes CPU, RAM, devices, and writable disks while disk sectors can be shared; it describes a **full-state restore contract**, not a full byte-for-byte disk copy on every snapshot. [Firecracker's snapshot documentation](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md) is for a separate Linux/KVM VMM and assigns disk-file lifecycle and snapshot trust to its operator. None of these published ratios can be combined without a new experiment with matched numerator and denominator.

## Decision sequence for this project

1. **Preserve correctness before optimizing.** Keep the existing baseline/fix, process/RAM restoration, sibling isolation, and host-private grading checks as gates. Add failure injection around save, clone, restore, and grading so incomplete infrastructure work remains pending rather than becoming policy reward 0.
2. **Measure the common critical path.** For branch counts 2 and 4, report p50/p95 disk clone, QEMU start, snapshot save/load, guest serial calls, hidden verifier, queue wait, and valid branches/hour. Charge warm-parent setup at several reuse counts. Publish the host, QEMU version, guest image digest, task revision, raw timings, and reward parity. The observed 2.581× serial and 1.565× two-sibling ratios measure different conditions; neither is the end-to-end RL-loop ratio.
3. **Choose the next sandbox optimization from the profile.** If branch creation dominates, explore concurrent child start or a hosted/Linux VM fork, subject to identical state and security checks. If repeated per-case restores dominate, investigate a safe verifier scheduling design without losing independent case starts. If dependency materialization dominates across many repositories, apply checksum-pinned pre-caching before replacing the VM isolation boundary. If multi-turn checkpoint traffic dominates, investigate selective state capture only after no-false-negative recovery testing.
4. **Choose training-system work only after there is a trainer.** The current export lacks token-level behavior log probabilities and policy updates. If later generation and optimization overlap poorly, [AReaL](https://arxiv.org/html/2505.24298) and RollArt provide candidate async designs, but policy revision, behavior probabilities, token masks, and a measured staleness bound must accompany them. Compare valid trained tokens and held-out task success per wall-clock hour, not only sandbox starts per second.

This microVM path improves the rate of **real, immediately verifiable coding episodes**. It cannot make an event next week occur sooner. Any transfer from coding practice to forecasting accuracy requires a separate, prospective held-out evaluation.

# Sandbox performance target and measured state boundaries

The measurements below retain their original frozen task and execution contracts. Most earlier QEMU coding A/B runs predate the [UID/GID 65534 candidate-Python binding](GUEST_IDENTITY_INTEGRITY.md); their historical timings must not be attributed to the newer identity contract. Earlier virtio graded A/B runs predate the QEMU-side disconnect gate and remain historical unsafe-prototype evidence. A new current-contract result is reported separately below.

The development host is a MacBook Pro with Apple M3, 8 GB of memory, QEMU 11.1.1/HVF, and an ARM64 Linux guest. We use the latest [DeltaBox v2 paper](https://arxiv.org/html/2605.22781v2) as a reference for the requested 5–6× hardware-tolerance target, while keeping its process-level state boundary separate from our QEMU full-VM operations. DeltaBox's event-weighted SWE-bench MCTS table reports **10.83 ms checkpoint API time** (asynchronous CRIU dump completion excluded and work overlapped with inference) and **1.86 ms warm-template restore** on a 96-core, 760-GiB server with 4-vCPU, 8-GiB Firecracker VMs. The paper's agent-perceived checkpoint blocking can be zero when that work fits inside the inference window.

Six times those paper numbers is approximately **65 ms checkpoint** and **11 ms restore**. This is a numerical target for our local experiment, not a matched hardware or semantic comparison. The [QEMU primitive report](measurements/microvm_primitives_v0.6.0.json) measured the following same-host HMP command roundtrips; it did not include boot, policy actions, or hidden grading:

| Configured guest RAM | `savevm` p50, two samples | `loadvm` p50 / p95, 20 samples | Against the 6× numerical target |
| --- | ---: | ---: | --- |
| 128 MiB | 90.09 ms | 48.13 / 63.92 ms | Above both thresholds |
| 256 MiB | 123.54 ms | 51.11 / 69.05 ms | Above both thresholds |
| 512 MiB | 218.59 ms | 81.95 / 244.16 ms | Above both thresholds |

Every load restored both a guest RAM marker and an ext4 disk marker. A separate 512-MiB run had a 161-ms load median, so these are descriptive single-host measurements rather than stable hardware limits. QEMU restores a whole VM; DeltaBox switches an in-guest filesystem layer and forks a process from a warm template. The operations cover different state and have different resource and trust assumptions. The earlier [guest-local `fork()` plus overlayfs experiment](measurements/guest_cow_branch_v0.6.0.json) completed a trusted process/file branch cycle in 0.988 ms median, but shares one guest kernel and mount namespace. A subsequent [private mount-namespace variant](measurements/guest_mount_namespace_v0.6.0.json) measured a **0.864 ms median / 0.990 ms p95** complete cycle over 200 repetitions, with separate mount views and unchanged shared lower repository. It still shares the guest kernel, runs trusted code, and has no independent per-branch host-private grading. The two guest experiments use different prepared assets and program revisions, so their medians are not a controlled before/after speedup; neither number can be substituted for a full-VM restore.

The [current guarded-runtime primitive rerun](measurements/microvm_primitives_currentguard_2026-09-25.json) binds exact source and pinned asset hashes and times the public wrappers separately from the HMP command. At 128 MiB, guarded save wrapper p50 was **97.18 ms** (two saves), and load wrapper p50/p95 was **48.47/69.00 ms** (20 loads). At 512 MiB, those values were **214.07 ms** and **67.39/222.92 ms**; one load took **331.63 ms**. Both sizes passed 23 RAM-and-ext4 resets. These current-source samples do not form a controlled before/after speed comparison with the historical table, and neither size meets the 6× numerical target for full-VM checkpoint and restore. The process/OverlayFS branch below is much faster under a narrower state and trust contract.

For the one pinned Boltons task whose hidden Python cases are explicitly declared stateless, an [opt-in guest verifier](STATELESS_VERIFIER.md) retains host-private expected outputs and starts every case in a fresh mount and PID namespace. Seven rotated, same-host comparisons with exact per-case result parity measured a **1.825 s median** to grade 14 cases with full-VM restore before each case, versus **0.336 s** for one guest batch with a fresh namespace per case: **5.433× faster for the graded-case stage**. This trades the general full-VM per-case restore contract for a narrower task-specific one; its common initial restore, VM setup, policy actions, model inference, and optimizer work are outside that timing. It cannot be compared directly with DeltaBox's checkpoint or restore API latency.

The measured whole-environment effects are smaller than the millisecond primitive alone suggests. Reusing a full VM for one scripted Boltons episode gave a [2.581× median steady-state ratio](measurements/microvm_boltons_v0.6.0.json) against a cold VM; independent warm sibling VMs gave a [1.565× median two-branch ratio](measurements/microvm_fork_boltons_v0.6.0.json) against parallel cold siblings. Within the warm-fork path, starting two children in parallel improved the fork stage, but the [complete graded batch](measurements/microvm_parallel_fork_boltons_v0.6.0.json) improved only 1.061× because the 14 host-private cases per branch dominate. A separate [reusable template experiment](measurements/microvm_template_boltons_v0.6.0.json) could spawn children after closing the parent: its two-pair median graded batch improved 1.743× over parallel cold VMs, or 1.171× after charging the one-time template setup. In a new [three-pair, four-sibling comparison](measurements/microvm_template_four_siblings_v0.6.0.json), the same template path took 11.532 s median versus 15.063 s for four parallel cold VMs, a 1.306× steady-state ratio; charging 6.039 s of template setup reduced the observed ratio to 1.125×. All four branches retained independent RAM/ext4 markers and the expected `[1, 0, 1, 0]` rewards. More simultaneous VMs on this 8-GB host did not preserve the two-sibling ratio. These use one already-solved public repository and scripted actions. None is a measured RL model-training gain.

The distinct [Humanize Docker verifier-worker A/B](measurements/realworld_humanize_verifier_workers_ab_2026-09-25.json) tested a second solved public repository. Across three alternating pairs per baseline/repair mode, all 12 graded episodes had identical within-mode action observations, 14 case results, image/source hashes, and rewards. On the repaired task, four case workers reduced median verification from **2.190 to 1.098 s** (2.00×) and complete episodes from **3.222 to 2.130 s** (1.51×) against one worker. All three paired repair differences favored four workers. The baseline complete-episode result had one cold/outlier observation, so it does not support a broad throughput claim. These Docker measurements are separate from the QEMU/VM comparisons and include no policy inference or optimizer.

An independent [two-child full-VM verifier-pool proof](../examples/realworld_boltons26/FULLVM_VERIFIER_POOL_RESULTS.md) held the Boltons task and full-state per-case restore contract fixed while distributing the 14 hidden cases across two cloned QEMU children. Five alternating pairs per repair/baseline mode completed 20 graded episodes with exact action, case, source, evidence, and reward parity and an independent RAM/ext4 preflight. The pool was slower on this 8-GB host: median complete episodes **7.212 s serial / 7.788 s pool**, and hidden verification **1.477 / 2.092 s**. Forking the two children cost **0.716 s median**, while the maximum sampled sum of QEMU RSS rose from **442,832 to 932,688 KiB**. This is a same-contract negative result; the proof remains separate from the production verifier.

The opt-in stateless path also ran through six complete `RealWorldEnv` episodes in three alternating pairs. Each scripted repair scored 1.0 over the same 14 host-private cases. Its verification median fell from 1.946 s to 0.451 s, while the full graded episode fell from 8.371 s to 7.267 s, a **1.152× episode ratio**; the three paired ratios ranged from 1.138× to 1.166×. The opt-in path spends extra time preparing trusted guest code and checking that the submitted state has no new persistent processes. This is the stronger training-environment throughput denominator on this fixture; it still omits model generation and weight updates.

The [prepared `RealWorldEnv` template](PREPARED_MICROVM_ENV.md) removes repeated guest boot while retaining independently restored child VM state. On the final current-code three-pair run, default full-VM hidden grading had **8.117 s cold / 3.647 s prepared** median complete episodes, a **2.226×** steady-state ratio; charging the 6.100-s template setup over six episodes reduced it to **1.800×**. Combining the explicitly declared stateless verifier with a preinstalled generic helper gave **7.029 s cold / 2.122 s prepared**, a **3.313×** steady-state ratio and **2.197×** after its 6.286-s setup. Each repair/baseline pair retained identical opening observations, every policy-action observation, all 14 hidden-case results, and rewards `1/0`. A matched helper-only A/B measured **2.256 s ordinary upload / 2.080 s preinstalled**, or **1.085×** steady state and **1.032×** including separate template setup. These are three-pair same-host environment comparisons on one solved public fixture, with neither model inference nor parameter training.

A [separate five-repetition replication](measurements/prepared_stateless_stability_5pair_v0.6.0.json) of the composed prepared-plus-stateless condition produced 10 cold and 10 prepared complete episodes. Its medians were **6.824 s cold / 1.935 s prepared**, a **3.525×** steady-state ratio; charging 6.353 s of template setup to the 10 prepared episodes yielded **2.591×**. That overall median mixes two scripted action lengths: the five repaired episodes had **7.101/2.323 s** cold/prepared medians (**3.056×**), while the five untouched baselines had **6.583/1.603 s** (**4.107×**). Each matched repaired/baseline pair had exact opening, action-observation, hidden-case, and reward parity. This uses the same one-host public fixture and does not expand the task distribution. We keep its samples separate from the earlier three-pair comparison.

The [v2 bounded-edit experiment](SMALL_EDIT_MICROVM.md) adds a SHA-bound `replace_text` action and eliminates one redundant restore from the opt-in stateless path. Its final [five-repetition report](measurements/prepared_small_edit_v0.7.0.json) contains 40 complete, parity-checked QEMU episodes: the bounded-edit method took **6.577 s cold / 1.728 s prepared** median across repair and untouched branches, with a **3.800× ratio of total times** at steady state and **2.751×** after charging 6.610 s of one-time preparation to its 10 prepared episodes. Repaired branches alone took **6.637 / 1.752 s**. Every repair scored 14/14 and reward `1`; every untouched branch scored 7/14 and reward `0`. This is a different frozen task/tool contract from the earlier v1 reports, so the samples are not pooled. The episode ratio is distinct from the paper-relative checkpoint/restore latency tolerance and contains no model inference or optimizer time.

A [controlled five-pair template-hash A/B](measurements/prepared_template_hash_ab_v0.8.0.json) held the v2 task SHA fixed, alternated legacy and child-check-only source-hash schedules, and checked exact cross-variant semantics across **80 QEMU episodes**. The 20 prepared episodes per variant totaled **36.632 s legacy / 31.280 s child-check-only**, **14.6% less wall time** or **1.171× throughput**. Prepared mixed-branch medians were **1.895 → 1.667 s** for full-file writes and **1.656 → 1.451 s** for bounded replacement; replacement repair-only medians were **1.734 → 1.462 s**. All 20 paired prepared deltas favored the candidate. Cold-control totals were 133.360/133.028 s, close relative to the prepared reduction. The new spawn path still hashes every cloned child disk against the pinned manifest before boot and rejects corrupt source/child or between-clone mutation in offline fault tests. It stops rereading the source template after a verified clone; if that source changes afterward, the already verified child is unaffected and a later spawn rejects the mismatch. This changes host provisioning time, not the QEMU save/restore operation, and the A/B uses one solved task on one host.

A newer [same-contract stateless case-upload A/B](STATELESS_BATCH_UPLOAD_AB.md) combined three guest shell calls into one bounded command without changing task SHA, UID/GID 65534 execution, observations, evidence kind, cases, or reward between arms. Across 12 complete QEMU episodes, the paired upload stage saved about **4.97 ms median** in five of six pairs. Six-episode totals were **10.714 s serial versus 10.519 s one-command** (1.018×); charging the shared 6.593-s template setup to both arms gave 1.011×. Complete-episode paired differences changed sign, so this is a small stage improvement, not a demonstrated training or whole-episode gain. Its effective task/helper binding is newer than the earlier v2 reports; their timing samples are not pooled.

A separate one-pair calibration using the public A/B script recorded 171,835,392/171,900,928-byte legacy/candidate template files. Its 12 legacy source-template SHA passes took **0.0679 s median each**, totaling **0.819 s** over four prepared legacy episodes. The files differ slightly in size because each condition independently prepares a VM template; this calibration has a separate task digest and is not pooled with the five-pair A/B.

The [QEMU restore-validation A/B](QEMU_RESTORE_VALIDATION.md) removes a repeated read-only disk SHA pass and monitor listing on an in-process saved tag, but still calls `loadvm` for every full-state restore. In the synchronized 40-pair run, strict/cached validation overhead p50 was **13.28/0.17 ms** and whole-call p50 was **124.11/87.20 ms**; an earlier 20-pair run had a worse cached p95. The robust result is redundant validation removal, not a stable full-restore or graded-episode throughput gain.

The [cooperative guest checkpoint experiment](../examples/cooperative_guest_checkpoint/README.md) now couples a quiescent Python heap and frozen OverlayFS view within a booted VM. Ten checkpoints and 100 independent branch restores passed process, filesystem, namespace, whole-outer-tree, and host-private reward checks. Restore-to-ready p50 was **0.470 ms**, and the 98 no-case branch cycles had **1.026 ms** p50 including scripted action and cleanup; the first two branches separately graded 14 cases each. The same booted 512-MiB VM's full `load_snapshot` wrapper had **103.795 ms** p50 across 30 restores. The fast process/overlay path shares a guest kernel, assumes trusted code and quiescence, does not survive VM death, and does not provide the CPU/RAM/device/disk recovery of `loadvm`. These are separate state contracts, so dividing their times does not establish a 5–6× same-contract improvement.

The [graded cooperative RealWorldEnv A/B](../examples/cooperative_realworld/README.md) extends that mechanism to successive policy actions and 14 host-private cases. Five alternated repetitions produced **10 matched pairs / 20 graded episodes** with exact common action, per-case, and reward parity for repaired and untouched branches. The control was a prepared full-VM child with an opt-in stateless verifier: it restores a VM once, then grades cases in separate guest namespaces rather than calling `loadvm` for every case. Complete-episode medians including teardown were **0.810 s cooperative / 1.647 s prepared full-VM child** (2.035× ratio of medians); all 10 paired deltas favored the cooperative arm, with a **0.849 s** median difference. One-time setup was **6.886/6.471 s**; totals for 10 episodes per arm including setup were **14.917/23.315 s** (1.563× ratio). Child provisioning, guest transport, grading implementation, and trust/state boundaries differ, so the episode ratio is not attributable to the checkpoint primitive alone; one solved task on one host cannot establish general RL throughput. A separate [20-pair ext4-plus-overlay A/B](WORKSPACE_OVERLAY_AB.md) measured **4.517 → 0.0703 ms** median workspace preparation against tar extraction in one already-booted guest. Its **64.3×** ratio is only for preparation, excluding branch action, grading, cleanup, boot, and training.

The [standalone read-only virtio RPC probe](MICROVM_ENV.md#opt-in-read-only-virtio-action-transport) removed repeated guest shell process starts from one bounded file-read implementation. A real-QEMU 100-pair A/B checked the complete read observation in all 110 warmup/measured pairs. Median serial-shell read was **70.447 ms**, versus **0.511 ms** for the persistent Python agent; an empty shell command and framed `PING` measured **2.890/0.230 ms**. These are two full read implementations, not pure wire latencies or checkpoint costs. The 5.719-s boot and the policy adapter's whole-workspace symlink scan were outside that timing. A subsequent [historical graded A/B](VIRTIO_GRADED_AB.md) included the scan and exact observation, hidden-case, and reward checks. Its [preinstalled-agent follow-up](VIRTIO_PREINSTALLED_IMAGE_AB.md) reduced five read actions from **160.374 to 17.485 ms**, but whole episodes were **7.344 versus 7.328 s** with mixed paired signs. A later QEMU-side check found that the device could still report `host=on` after STOP and host socket close, so those runs remain historical unsafe-prototype evidence. The [final-source hardened A/B](measurements/virtio_hardened_checkpoint_ab_2026-09-25.json) used the current UID/GID 65534 candidate contract, unlinked the host socket, and attested QEMU disconnection before and after each snapshot. In three alternating five-read real-QEMU pairs, all opening/action observations, 14 case results, final source hashes, and rewards matched; each episode made one save and 14 loads without fallback. Median reads were **184.497 versus 20.624 ms** (8.946×), while median complete episodes were **7.625 s serial versus 7.786 s virtio**. All three paired virtio episodes were slower. The opt-in transport now satisfies the tested checkpoint boundary but does not improve whole-episode throughput.

The [resident guest `RealWorldEnv` adapter](../examples/resident_guest_candidate/README.md) completed batch and sequential real-QEMU smokes with exact 14-case repair/baseline grades, namespace isolation, and an ordinary adversarial timeout scored zero instead of pending. It remains a pinned, stateless, trusted-guest integration example rather than a repeated throughput A/B or general sandbox. End-to-end learned-policy throughput must include model inference, full verification, and optimizer updates; none of these experiments yet measures that loop.

The [Crab-inspired asynchronous completion gate](ASYNC_VM_CHECKPOINT.md) uses the real QEMU `savevm` plus fsynced journal on every pre-submit turn, but overlaps that work with an observation-only simulated policy wait. In the current two-pair A/B at 100 ms wait per turn, six overlapped turns exposed **0.006826 s** total checkpoint gate wait; at 0 ms they exposed **0.528095 s**. Both conditions preserved exact action observations, all 14 case results, rewards, and checkpoint counts. The two 100-ms paired whole graded-episode deltas were **+0.286 s and +0.503 s**; the zero-wait deltas were **+0.117 s and -0.157 s**. This verifies that the gate can hide checkpoint work inside an available wait, but does not establish a stable complete-episode or RL-training speedup.

The [Humanize cooperative RealWorldEnv replication](../examples/cooperative_realworld_humanize/README.md) uses a second pinned public repository under the same broad comparison design. Five alternating repetitions gave **10 matched pairs / 20 graded QEMU episodes**, with exact common action observations, 14-case outcomes, submitted source, and reward parity. Median complete episodes including cleanup were **0.619 s cooperative / 1.223 s prepared full VM** (1.975× ratio of medians); every paired difference favored cooperative. One-time setup was **6.414/6.282 s**, and observed totals for ten episodes per arm including setup were **12.565/18.609 s** (1.481×). This is a process/OverlayFS shared-kernel path against an independent full-VM child; it is neither same-contract checkpoint latency nor GPU training throughput. The [terminal QEMU-crash recovery](TERMINAL_VM_CRASH_RECOVERY.md) and [snapshot transaction guard](SNAPSHOT_TRANSACTION_GUARD.md) add correctness checks without a matched latency A/B.

The [stable-revision rollout fence A/B](ROLLOUT_REVISION_FENCE.md) ran three alternating two-episode Docker batch pairs with equal action and reward evidence. Median batches were **5.876 s default / 6.075 s fenced**; the fence was slower in two pairs and had no demonstrated collection-speed advantage. It prevents stale trajectories from being rewarded or exported when a policy revision changes; a real versioned model and optimizer were outside this measurement.

The [durable rollout verification A/B](DURABLE_ROLLOUT_SERVICE.md) ran three separate-process SQLite queue batches against the same two-episode in-memory control, alternating order. All 12 graded episodes matched their repair/baseline reward, every hidden case, final source, and visible action-observation digest. Median complete batch walls were **9.728 s in memory / 9.890 s durable** (durable/control throughput ratio **0.984×**); a **17.157-s** durable tail means this small pilot does not show a speedup. A verifier killed after case execution but before reward commit was recovered by attempt 2 without double publication. This adds a tested process-death boundary, not trainer or GPU throughput.
